# Phase 6 — Information Architecture (IA)
### STEP IIT KGP Incubation Management Platform

> IA defines how the platform's content and functions are **organized, labeled, and navigated** —
> per role. It groups the surfaces surfaced in Phase 5 into coherent zones, defines global vs.
> role-scoped navigation, and establishes labeling and URL conventions that the Sitemap (Phase 7)
> and Frontend (Phase 10) build on.

---

## 1. Top-level zones

The platform is one application with **four IA zones**, gated by authentication + RBAC:

| Zone | Audience | Auth | Root path |
|------|----------|------|-----------|
| **Public** | Everyone (P9) | none | `/` |
| **Account / Auth** | Registering/returning users | partial | `/auth/*` |
| **App (role portals)** | Authenticated users (P1–P6) | required | `/app/*` |
| **Admin console** | Administrators, Super Admin (P7, P8) | required + role | `/admin/*` |

Rationale: a hard `/admin` boundary keeps no-code operations (CMS, form engine, cycles) isolated,
audited, and independently protectable; `/app` hosts everyday role portals; `/` stays lean, fast,
and fully CMS-driven for SEO and trust.

---

## 2. Public zone IA (CMS-driven)

Primary nav (editable in CMS → Navigation):
- **Home** `/`
- **About** `/about` (vision, mission, director's message, facilities)
- **Startups** `/startups` (public Showcase/Directory) → `/startups/[slug]`
- **Programs / Incubation** `/programs`
- **News & Events** `/news`, `/events` → detail pages
- **Resources / Downloads** `/resources`
- **FAQ** `/faq`
- **Contact** `/contact`
- **Apply** `/apply` (primary CTA → auth → wizard)

Footer (CMS): quick links, contact details, partners, social links, legal. SEO metadata per page.

**Content model behind Public zone** (managed in Admin CMS): singletons (Home, Director message,
Vision/Mission, Footer, Contact, Navigation, SEO) + collections (Facilities, Gallery, Events, News,
Downloads, FAQ, Partners, Showcase entries). Every item has draft/published + version history.

---

## 3. App zone IA (role portals under `/app`)

A shared shell (top bar + role-aware sidebar + notification center) renders **only** the sections a
user's role permits. Menus are permission-derived, not hardcoded per role.

**Applicant (P1/P2/P3)**
- Dashboard `/app` — applications across cycles + status tracker
- Application `/app/applications/[id]` → wizard steps `/app/applications/[id]/[step]`
- Business Plan `/app/applications/[id]/business-plan/[section]`
- Documents `/app/applications/[id]/documents`
- Review & Submit `/app/applications/[id]/review`
- Notifications `/app/notifications` · Profile `/app/profile`

**Reviewer (P4)**
- Dashboard `/app/review` — assigned queue
- Review Portal `/app/review/[applicationId]` (tabs: Summary · Documents · Business Plan · Founders ·
  Timeline · Notes · Score · History)

**Mentor (P5)**
- Dashboard `/app/mentor` — assigned incubatees → `/app/mentor/[incubationId]` (milestones, notes)

**Incubation Staff (P6)**
- Lifecycle Board `/app/staff/pipeline` (Kanban by state, per cycle)
- Application detail (staff view) `/app/staff/applications/[id]`
- Incubation records `/app/staff/incubation/[id]` (mentor, office, funding, milestones, schedule)
- Assignments (reviewers/mentors) · Showcase publish action

**Director / Super Admin (P8)** — reports live under Admin (see §4) but reachable from `/app` too.

Shared: global search (scoped by role), notification center, profile/settings.

---

## 4. Admin console IA (`/admin`)

Grouped by function; visibility gated by permission:

- **Dashboard** `/admin` — operational overview + reports entry
- **Content (CMS)** `/admin/cms` — Pages/singletons, Collections (events, news, facilities, gallery,
  downloads, FAQ, partners), Media library, Navigation, Footer, SEO, Showcase
- **Forms** `/admin/forms` — Form templates per cycle/category, Field builder, Option sets, Validation
- **Documents** `/admin/documents` — required-document sets per category
- **Cycles** `/admin/cycles` — cohorts (open/close, dates, template + scorecard + document binding)
- **Scorecards** `/admin/scorecards` — criteria + weights
- **Applications** `/admin/applications` — all applications, filters, lifecycle config
- **Users & Roles** `/admin/users`, `/admin/roles` — RBAC management (Super Admin)
- **Reports** `/admin/reports` — dashboards + exports (FR-N)
- **Audit Log** `/admin/audit` — queryable trail (FR-O)
- **Settings** `/admin/settings` — system config, notification templates, (future) tenants

## 5. Labeling & taxonomy conventions

- **Nouns for zones/objects** (Applications, Cycles, Scorecards); **verbs for actions** (Submit, Publish, Assign).
- **Consistent object language** across roles: an "Application" is the same object everywhere; role
  determines the *view*, not the vocabulary.
- **Status labels** mirror the lifecycle states exactly (Draft, Submitted, Screening, Under Review,
  Presentation Scheduled, Interview, Selected, Rejected, Agreement Pending, Incubated, Monthly Review,
  Graduated, Archived) — one canonical set, surfaced with color-coded badges.
- **Taxonomies (admin-managed, reusable):** Sectors, Categories (Student/Faculty/Staff/External),
  Document types, Scorecard criteria, Cycle years.

---

## 6. Navigation model

- **Global (public):** CMS-driven primary nav + footer.
- **App shell:** role-aware sidebar (permission-derived) + top bar (search, notifications, profile).
- **Admin shell:** grouped sidebar (Content / Applications / Config / System) + breadcrumb.
- **Contextual:** wizard step-rail (application), tabbed sub-nav (review portal), Kanban columns (pipeline).
- **Cross-links:** application ↔ business plan ↔ documents ↔ review; incubation ↔ showcase entry.

---

## 7. URL & routing conventions

- Public: clean, SEO-friendly slugs (`/startups/acme-robotics`).
- App: `/app/<portal>/<object>/[id]/<subview>`.
- Admin: `/admin/<function>/<object>/[id]`.
- IDs are opaque (cuid/uuid); slugs only for public content.
- Every mutating route is server-side authorized + audited (Phase 9).

---

## 8. IA principles (carried into design)

1. **One object, many views** — role changes lens, not data model.
2. **Config lives in Admin, content lives in CMS, work lives in App** — clean separation of concerns.
3. **Permission-derived menus** — no dead links; users never see what they can't use.
4. **Everything versioned** — content, forms, applications keep history; navigation never destroys past state.
5. **Progressive disclosure** — dashboards summarize; detail pages go deep; wizards chunk complexity.
